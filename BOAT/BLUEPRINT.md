# BOAT Blueprint

**Version:** 0.1.0  
**Phase:** 0 — foundation and baseline  
**Status:** Proposed architecture; implementation not yet started

## 1. Mission

Build a reliable editorial operations agent that helps TrendForge publish accurate, useful, timely articles and continuously improve through evidence-backed evaluation. BOAT should find problems, explain them, propose a minimal repair, test the repair, request the required permission, and preserve a complete audit trail.

BOAT is not allowed to optimize for publication volume by lowering factual, editorial, source, or safety standards.

## 2. System context

BOAT is a controlled layer alongside existing TrendForge systems. It should reuse existing artifacts and validators where their contracts are verified; it must not duplicate or silently replace them.

## 3. Core modules

### 3.1 Observer and Artifact Collector
- Read published Markdown/JSON, evidence packs, claim-verification outputs, editorial reports, workflow logs, run metadata, and source links.
- Record source paths, content hashes where practical, timestamps, workflow run IDs, and commit SHAs.
- Distinguish missing data from a clean result; missing evidence is never a pass.
- Prefer artifacts already generated by CI before requesting new provider calls.

### 3.2 Evidence Auditor
- Extract factual claims into stable claim IDs.
- Link each claim to exact source URLs and relevant supporting passages when available.
- Classify outcomes: supported, contradicted, insufficient evidence, stale, misattributed, uncertain, or not yet checked.
- Separate source publication date, event date, forecast/opinion, and confirmed outcome.
- Never present a forecast or reported possibility as a confirmed event.
- Require re-verification after any article repair.

### 3.3 Article Doctor
- Diagnose factual errors, unsupported details, wrong units/currency/scale, attribution drift, missing context, misleading certainty, repeated sentences, empty headings, weak structure, and unclear writing.
- Produce a finding with severity, evidence, affected text, confidence, recommended action, and whether a human decision is required.
- Start in read-only mode. A diagnosis is not permission to edit.

### 3.4 Editorial Benchmark Lab
- Compare TrendForge articles with selected human-written reference articles on accuracy, source quality, context/depth, specificity, attribution, organization, clarity, originality, and reader value.
- Store rubric scores, examples of editorial techniques, and provenance.
- Learn general patterns (e.g., better attribution or more useful context), not copied paragraphs, distinctive phrasing, or article structure line-for-line.
- Account for topic, article length, publication time, source availability, and article type before comparing scores.

### 3.5 Learning Engine
- Convert a verified incident into a hypothesis: observed failure → root-cause candidate → proposed change → fixture/regression test → measured outcome.
- Label evidence strength and sample size; do not generalize from a single failure without qualification.
- Maintain versioned experiments and before/after metrics.
- Keep new learning in shadow mode until it passes historical regression tests and is explicitly approved.
- Never autonomously rewrite its own safety policy or reduce a gate because the gate blocks an article.

### 3.6 Trend Prioritizer and Targeted Work Queue
- Score candidate urgency, source readiness, novelty, relevance, freshness, and duplication risk.
- Support a candidate-specific workflow only after a separate implementation and quota/safety review.
- Preserve the normal six-hour scheduled pipeline as a fallback.
- Deduplicate candidates and runs; set concurrency limits, cooldowns, and a clear budget ceiling.
- Urgency can prioritize work but cannot bypass evidence or publication gates.

### 3.7 Permission and Action Gateway
- Present a precise proposed action, affected files/articles, rationale, evidence, diff, risk level, expected cost, tests, expiry, and rollback plan.
- Support approve, reject, and request-changes outcomes.
- Bind approval to an immutable proposal/version so changed diffs require renewed approval.
- Execute privileged actions server-side through a protected GitHub workflow or authenticated app; never embed secrets in static JavaScript.
- Record actor, time, scope, proposal hash, result, and links to run/PR/commit.
- A one-button approval is a UI goal, not a shortcut around authentication or authorization.

### 3.8 Project Memory and Audit Trail
- Keep Markdown records understandable to a human and machine-readable event records for repeatable history.
- Each material step should record: timestamp, objective, baseline, files inspected/changed, hypothesis, action, tests, result, decision, commit/PR/run links, risks, and next step.
- Separate verified facts, hypotheses, decisions, and unresolved questions.
- Never claim a test passed unless its actual result is available.

## 4. Operating modes

1. **Observe (Phase 0–1):** read-only collection and reporting.
2. **Recommend (Phase 1–2):** propose ranked fixes with evidence; no production mutation.
3. **Sandbox (Phase 2–3):** run repairs and learning experiments against fixtures/temporary copies.
4. **Approval-gated action (Phase 3–4):** perform explicitly approved, isolated changes and open a PR or run a bounded workflow.
5. **Limited autonomy (Phase 5):** only low-risk, reversible actions with measured reliability, explicit scope, quotas, and a kill switch. Publication and gate changes remain separately controlled.

Mode changes require documented acceptance criteria and approval.

## 5. Trust and safety boundaries

- Existing evidence, claim verification, editorial quality, image safety, and build/release gates remain authoritative.
- No gate may be disabled, softened, skipped, or reinterpreted by BOAT.
- Article repair must preserve source lineage and rerun the same relevant validators.
- No autonomous deletion, public publishing, merging, secrets changes, dependency upgrades, or policy-threshold changes in the initial release.
- If a source is unavailable, conflicting, or weak, BOAT must state the limitation and recommend hold/review rather than inventing certainty.
- Keep user approval separate from technical validation: approval permits an action; it does not make the result correct.

## 6. Data contracts (proposed)

Each finding should contain:
- `finding_id`, `created_at`, `article_id`, `article_revision`
- `category`, `severity`, `status`, `summary`
- `affected_claim_ids`, `source_refs`, `evidence_excerpt_refs`
- `confidence`, `rationale`, `recommended_action`
- `requires_approval`, `validation_plan`, `audit_event_id`

Each action proposal should contain:
- `proposal_id`, `proposal_hash`, `action_type`, `scope`, `diff_ref`
- `rationale`, `evidence_refs`, `risk_level`, `expected_cost`
- `required_checks`, `rollback_plan`, `expires_at`
- `approval_status`, `approval_actor`, `approval_timestamp`
- `execution_ref`, `outcome`

These contracts are design proposals and should be validated against existing repository conventions before implementation.

## 7. Integration plan

- Read existing memory, learning, supervisor, audit, claim verification, evidence, editorial, and workflow artifacts first.
- Keep BOAT components isolated under a dedicated directory/module boundary until interfaces are understood.
- Prefer a deterministic library/CLI layer before building a chat UI.
- Add the Control Center workspace only after there is a secure server-side action path; static export alone cannot safely execute privileged actions.
- Use mock/fixture tests for failures, provider unavailability, contradictory sources, stale articles, duplicate urgent topics, rejected approvals, expired approvals, and failed post-repair verification.
- Do not introduce a new paid model requirement in Phase 0.

## 8. Acceptance criteria

A BOAT release is not accepted merely because code runs. It must demonstrate:
- Traceable claim-to-source evidence.
- Correct handling of unsupported/contradicted/uncertain claims.
- No gate bypass under any tested failure path.
- Repair followed by successful re-verification, or an explicit blocked result.
- Duplicate task suppression and bounded workflow dispatch.
- Approval tied to the exact proposal and immutable diff.
- Durable audit records for both success and failure.
- Regression tests using saved examples, including known unit/scale and attribution errors.
- Clear distinction between observed facts and inferred hypotheses.
- Measured performance against a baseline before increasing autonomy.
